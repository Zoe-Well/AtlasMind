## 建议结论

下一阶段不建议立即扩张功能范围。最有价值的工作是把现有能力变成稳定、可重复验证的真实闭环：先统一质量门禁并消除环境耦合，再验证“上传真实文档 → 建索引/图谱 → 授权问答 → 引用证据 → 运行审计”的完整链路。SQL 连接器、复杂 RAG 策略编辑和独立向量数据库应排在这条闭环稳定之后。

## P0：稳定工程基线

目标：任何开发者和 CI 都能用一致命令获得可解释、可重复的结果。

### 1. 修复测试环境隔离

- 让 Settings 测试显式禁用项目 `.env`，或通过统一 fixture 使用隔离配置。
- 保留生产配置校验，不通过弱化校验让测试通过。
- 将当前两个受 `.env` 污染的测试加入回归验证。

**验收出口**：从仓库根目录运行测试时，不依赖开发者个人 `.env` 内容；相关配置测试稳定通过。

### 2. 建立单一质量门禁

- 实现 `scripts/quality_gate.sh` 或等价跨平台入口。
- 后端统一运行 Ruff、mypy、unit、contract、security、integration 和 evaluation。
- 前端统一运行 typecheck、ESLint、Vitest 和 production build。
- Playwright 截图作为可选视觉任务，关键交互 E2E 作为必需任务。
- 扩展 GitHub Actions，避免当前 CI 只覆盖部分后端测试。

**验收出口**：本地和 GitHub Actions 使用相同检查集合；失败能明确定位到具体门禁。

### 3. 加入 API 契约治理

- 对 OpenAPI 3.1 执行 lint。
- 固化契约快照和 breaking-change 检查。
- 验证前端 `schema.d.ts` 与当前 OpenAPI 同步。

**验收出口**：不兼容 API 变更会在合并前失败；生成客户端不存在未提交漂移。

## P1：闭合真实 MVP 链路

目标：使用真实基础设施和模型端点完成可重复的业务验收，而不仅是演示数据或单模块测试。

### 4. 固化真实知识库烟雾测试

覆盖以下顺序：

1. 上传受支持文档；
2. 原文件写入 MinIO；
3. PostgreSQL 中生成版本、分块和向量；
4. Neo4j 中生成可追溯实体关系；
5. 使用当前授权范围发起问答；
6. 返回可定位引用，并在右侧证据面板展示；
7. AgentRun、trace 和审计事件能够关联；
8. 重启后仍可检索，撤销版本后不再返回旧证据。

**验收出口**：在 Compose 环境一键执行并形成机器可读报告；无演示数据回退。

### 5. 完成企业身份联调

- 选定目标 OIDC 提供方并验证登录、登出、刷新、过期和权限变更。
- 明确员工、知识管理员、审批人和审计员的角色映射。
- 验证跨用户运行记录和受限知识的零泄露。

**验收出口**：目标 IdP 的测试租户通过权限矩阵和会话生命周期测试，生产仍禁止 local auth。

### 6. 将核心前端从演示数据切到真实 API

优先顺序建议为：`/chat` → `/knowledge` → `/runs` → `/approvals` → `/graph` → `/evaluations`。

**验收出口**：核心用户旅程在无演示数据时可完成；加载、空态、失败、降级和无权限状态均有自动化覆盖。

## P2：生产就绪与规模验证

### 7. 建立相关性和质量基线

- 建立中英文关键词、向量、融合、重排和 Graph 多跳黄金集。
- 固化 Recall@k、MRR、nDCG、忠实度、上下文相关性和引用准确率阈值。
- 为业务数据集指定维护人和版本策略。

**验收出口**：每次检索或 Prompt 变更都能与上一基线比较，安全零容忍指标不能被平均分掩盖。

### 8. 验证性能与容量目标

- 验证 90% 基础问答 10 秒内完成。
- 验证 95% 支持文件 10 分钟内可检索。
- 验证 85% 多源任务 60 秒内给出可核验结论或准确降级。
- 覆盖 100 并发运行、百万文档容量估算和 Neo4j 投影窗口。

**验收出口**：形成可复现测试脚本、环境规格、p50/p95/p99 和瓶颈结论。

### 9. 完成恢复、安全和供应链门禁

- 演练 PostgreSQL/对象恢复、outbox 重放和 Neo4j 全量重建。
- 明确并验证 RPO/RTO。
- 加固非 root 容器、只读文件系统、健康检查和网络最小权限。
- 生成依赖锁审查、许可证清单和 SBOM。
- 固化数据保留、脱敏、导出、删除和外部 telemetry 决策。

**验收出口**：生产启动检查自动阻断缺少必需安全配置的部署，并有恢复演练记录。

## 暂缓扩展的能力

| 能力 | 当前建议 | 重新启动条件 |
|---|---|---|
| SQL 数据连接器 | 保持占位 | 文档知识库真实闭环稳定，并完成只读权限、审计和查询预算设计 |
| 可编辑 RAG 策略 | 先保持受控配置或只读展示 | 相关性基线稳定，能够证明策略变更不会绕过授权与质量门禁 |
| Qdrant | 暂不引入 | pgvector 的容量、p95 或维护窗口实测触发预设阈值 |
| 更多外部工具 | 暂不扩张 | 现有审批、幂等、超时、审计和失败恢复经过真实工具验收 |
| LangSmith | 保持可选 | 企业数据外发、脱敏、保留和合规责任明确批准 |

## 推荐的下一个迭代

建议将下一个迭代控制在三个交付物：

1. 修复 `.env` 对测试的污染，并提供单一质量门禁命令；
2. 将完整后端与前端检查接入 GitHub Actions；
3. 在 Compose 真实环境固化一次“上传 → 检索/Graph → 授权回答 → 引用/审计”的烟雾测试。

完成这三项后，项目会从“功能很多的 MVP”进入“可以安全持续迭代的 MVP”。

## 规划维护规则

- 每次功能完成后，从本文移除已完成建议，并将验证事实同步到 [PROJECT_STATUS.md](PROJECT_STATUS.md)。
- 新建议必须包含优先级、原因和可验证的验收出口；避免只记录模糊想法。
- 代码变更暴露新的风险、依赖或阻塞时，应在本次变更中更新本文。
- 优先级发生变化时必须写明依据；不得用本文擅自扩大 `spec.md` 的核心需求或验收范围。
- 每次更新必须修改“最后更新”日期。
