# Implementation Plan: 企业级 Agentic RAG 知识平台

**Branch**: `001-enterprise-agentic-rag` | **Date**: 2026-08-22 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification `specs/001-enterprise-agentic-rag/spec.md`

## Summary

构建面向企业内部员工的可信知识代理平台，按四个阶段交付基础企业 RAG、Agent 工作流与工具、
GraphRAG、Advanced RAG 与持续评估。系统采用模块化 Python Web Service 与独立 worker，保持
Agent 决策层和 Retrieval/Tool 执行层分离；所有证据、工具、图路径、引用和运行记录都执行
端到端授权。PostgreSQL 是规范事实源，Phase 1 使用 pgvector 并通过 port 保留迁移 Qdrant 的
能力；原始文件进入 S3 兼容对象存储，Neo4j GraphRAG 作为可重建图投影和图检索引擎。OpenTelemetry 提供
运行观测基线，DeepEval 与确定性指标共同构成质量门禁。

## Technical Context

**Language/Version**: Python 3.14（现有项目基线；关键依赖须先通过兼容性 smoke test）

**Primary Dependencies**: FastAPI、Pydantic、LangGraph、SQLAlchemy/Alembic、PostgreSQL driver、
pgvector、S3-compatible client、Neo4j driver、Neo4j GraphRAG for Python、OpenTelemetry、DeepEval、pytest；
模型、Embedding、Reranker 和企业身份系统通过项目自有 typed port 接入

**Frontend**: Next.js（App Router）+ React + TypeScript strict；Tailwind CSS 与 shadcn/ui/Radix UI
负责界面层，TanStack Query 管理服务端状态，React Hook Form + Zod 管理表单，Zustand 仅用于少量
客户端状态；依据 OpenAPI 生成类型化 API 客户端，AgentRun 进度首期使用 SSE。前端采用服务端
OIDC/BFF 会话，访问令牌不得写入 `localStorage`。该选型已通过 T147 实现，并扩展覆盖各阶段治理页面。

**Storage**: PostgreSQL + pgvector（规范状态、权限元数据、任务、向量与首期关键词检索），
MinIO/S3（不可变原始文件），Neo4j（Phase 3 可重建图投影）；Qdrant 仅在实测触发后启用

**Testing**: pytest 单元/契约/集成/安全测试，真实存储集成测试，版本化 RAG 回归数据集，
DeepEval 语义指标，以及引用、权限、审批和状态机的确定性验证

**Target Platform**: Linux 容器；同一应用镜像支持 API、ingestion worker、Agent worker 和
evaluation worker 进程角色；企业 OIDC/OAuth2 与受控模型端点为外部依赖

**Project Type**: 单仓库模块化 Web Service，公开版本化 REST API，内部使用 typed ports、
transactional outbox 与持久 worker 任务

**Performance Goals**: 与 spec 一致：90% 基础问题在 10 秒内完成；95% 支持文件在 10 分钟内
可检索；85% 多源任务在 60 秒内给出可核验结论或准确降级；99% 交互可追踪

**Constraints**: 未授权内容泄露为 0；高风险副作用未审批执行为 0；权限未知或过期时 fail closed；
引用必须定位到当前授权来源；每个 Agent 运行限制步骤、时间、token、工具次数和结果大小；
运行/审计/评估数据政策未批准时禁止上线

**Scale/Scope**: 初始企业内部部署基线为不超过 10,000 名员工、1,000,000 个文档和 100 个并发
Agent 运行；实际容量通过目标语料和工作负载测试校准，达到向量容量、p95 或维护窗口触发条件后
再评估 Qdrant 或服务拆分

## Architecture Decisions

### Real-data local MVP runtime

The executable local MVP uses `local` authentication only in non-production environments while all
knowledge artifacts remain real and persistent. FastAPI and a separate ingestion worker are composed
with PostgreSQL/pgvector, MinIO, Neo4j, and OpenAI-compatible chat/embedding endpoints. The runtime
contains no demo-data fallback: missing model capabilities leave the platform available but model-dependent
operations fail explicitly with `MODEL_CAPABILITY_NOT_CONFIGURED`, while the ingestion worker remains idle
without consuming queued work. Failed configured model/index/graph work keeps the ingestion job
non-searchable, and answers persist their evidence and citations. Production
continues to require OIDC and the governance gates defined by this plan.

### Neo4j GraphRAG integration boundary

The real-data runtime uses Neo4j GraphRAG for Python for entity/relation extraction, the
`Neo4jGraph`/`KGWriter` projection contract, vector-index management, and
`VectorCypherRetriever`. AtlasMind remains the system of record for canonical entity and relation
IDs, document versions, scope bindings, provenance, evidence, and citations. Before vector search,
the graph adapter resolves the entity IDs authorized by the caller's scopes and active document
versions and passes that allow-list into the framework retriever; post-retrieval filtering is not an
authorization boundary. The existing pgvector and PostgreSQL lexical index remain the primary
document-chunk retrieval path.

### Request and Evidence Flow

1. API 从可信身份系统验证令牌并创建不可被请求体覆盖的 `AuthContext`。
2. Application Use Case 建立 `AgentRun`、预算和 correlation ID。
3. 简单问答走确定性 Retrieval Pipeline；复杂任务由 LangGraph 产生 Capability Request。
4. 执行网关重新验证输入、权限、风险和审批，再调用具体 Retrieval/Tool adapter。
5. adapter 返回已授权 `EvidenceEnvelope` 或类型化失败；未授权内容不得进入 Agent state。
6. Answer Composer 只消费授权证据，区分事实、推断、冲突和未知，并生成 claim-bound Citation。
7. 输出前重新检查授权、引用有效性和敏感披露；OTel 与审计记录使用同一 correlation ID。

### Ingestion and Projection Flow

1. 上传只创建 Document、不可变 DocumentVersion、对象写入意图和 IngestionJob。
2. PostgreSQL 事务同时写入状态与 outbox；worker 使用幂等 key 领取任务。
3. worker 依次验证、解析、分段、提取元数据、生成向量和可选图投影。
4. 每种投影记录 generation、状态、来源版本和失败原因；失败内容不可检索。
5. 必需投影通过后原子切换 active version/SEARCHABLE；旧 generation 延迟清理。
6. 撤销或权限收紧先在 PostgreSQL 同步变为不可见，再异步删除派生投影。

### Deployment Roles

- **API**: 身份入口、命令提交、状态读取、答案与引用返回。
- **Ingestion Worker**: 文档处理、向量和图 projection、重试与 reconciliation。
- **Agent Worker**: 多步骤运行、工具审批暂停/恢复、预算与失败隔离。
- **Evaluation Worker**: 版本化数据集执行、指标汇总和门禁结果。

各角色使用相同领域代码与数据库迁移，部署时按负载独立扩缩。首期使用 PostgreSQL 持久任务和
outbox，不增加消息中间件；若吞吐与延迟测试证明需要，再通过 queue port 引入独立 broker。

## Phase Delivery Strategy

### Phase 1 — Enterprise RAG

- 企业身份、角色和 Knowledge Scope 映射。
- 文档上传、不可变版本、元数据治理、幂等导入与生命周期。
- pgvector + Lexical Retriever 混合检索、重排、证据充分性与引用。
- 查询前授权、返回前复核、无答案/冲突/失效来源处理。
- OTel、审计、基础权限测试与 RAG 回归集。

### Phase 2 — Agent Workflow and Tools

- LangGraph 有界状态机、步骤/时间/token/工具预算。
- Capability Registry 与统一执行网关。
- 注册数据集上的参数化只读查询和受控外部工具。
- 参数绑定的一次性人工审批、暂停/恢复与防重放。
- 多源综合、部分失败降级和工具安全回归。

### Phase 3 — GraphRAG

- 实体、关系、mention 与 provenance 构建。
- Neo4j GraphRAG 抽取、向量索引、Retriever 和 generation 投影适配。
- 路径级 scope 过滤、授权多跳查询与关系冲突治理。
- GraphRAG 正确性、虚构关系和权限侧信道评估。

### Phase 4 — Advanced RAG and Continuous Evaluation

- Policy-driven Query Rewrite、Self Query、HyDE 与 Context Compression。
- 策略版本、灰度、对照评估和快速关闭。
- 隐藏回归集、质量趋势和批准基线管理。
- 依据实测容量和检索质量决定是否启用 Qdrant 或拆分服务。

## Quality and Release Gates

- 任何受限 marker 出现在候选、prompt、答案、引用、错误、trace 或评估产物中均阻止发布。
- 缺失、过期、重放、换参或跨用户 Approval Grant 必须拒绝；未审批副作用必须为 0。
- 直接/间接提示注入不得改变 AuthContext、capability allowlist 或审批状态。
- 每次变更 prompt、model、chunking、embedding、reranker、retrieval policy、权限策略或工具 schema
  后必须运行固定隐藏回归集。
- RAG 指标不得低于 spec SC-001 至 SC-009；安全失败不可用平均质量分抵消。
- 评估输出必须记录代码、数据集、知识快照、索引、策略、模型、prompt 和 evaluator 版本。
- 企业保留/脱敏/删除政策及 LangSmith 外发决策未批准时禁止生产上线。
